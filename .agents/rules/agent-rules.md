# Reglas de equipo del proyecto

Estas reglas tienen alcance de proyecto y aplican a todas las contribuciones humanas y automatizadas. Cada justificación cita un hecho documentado en [notas-análisis.md](../../notas-an%C3%A1lisis.md#hallazgos); la última columna propone una tarea pequeña y verificable para comprobar la regla.

| Nombre | Alcance | Justificación | Guía específica del proyecto | Validación con una tarea pequeña |
|---|---|---|---|---|
| Períodos derivados de los datos | Frontend y cualquier vista que presente fechas | **A3/N2:** [App.tsx](../../frontend/src/App.tsx) fija `2024 - Full Year`, mientras [routes.py](../../backend/app/routes.py) genera fechas relativas al día actual. | Derivar el período de las fechas devueltas por la API o de un parámetro compartido. No dejar una etiqueta fija que pueda contradecir los datos. | Cambiar el encabezado para mostrar el primer y último mes de los movimientos cargados; ejecutar `cd frontend && npm test && npm run build` y comprobar que el texto coincide con la respuesta de `/api/metrics`. |
| Contratos de API explícitos | Cambios de rutas backend e integración frontend | **A2:** [App.tsx](../../frontend/src/App.tsx) consume solo `/api/metrics`, aunque [routes.py](../../backend/app/routes.py) define más endpoints analíticos. | Al añadir o cambiar una ruta, indicar si la interfaz la consume. Si no se integra, documentarla como API disponible pero no usada por el dashboard. | Añadir a [README.md](../../README.md) una línea de inventario para `/api/metrics/summary` que indique su estado de consumo; contrastarla con la ruta declarada en backend. |
| Separación entre demo y despliegue real | Backend, configuración y documentación de despliegue | **A1/A4/A5:** [routes.py](../../backend/app/routes.py) genera datos sintéticos; [main.py](../../backend/app/main.py) permite cualquier origen CORS; [Dockerfile](../../backend/Dockerfile) expone debugpy. | Tratar el generador como dato de demostración. Antes de usar datos reales o desplegar públicamente, definir persistencia y revisar CORS y depuración para el entorno objetivo. | Añadir al README una advertencia visible de que los datos son simulados y que la configuración actual es de desarrollo; verificarla contra el generador y la configuración del backend. |
| Nombres que describen el comportamiento | Tests, funciones, endpoints y textos visibles | **N1:** [test_routes.py](../../backend/tests/test_routes.py) nombra el resultado `full_year`, aunque el generador cubre 12 meses completos móviles. | Nombrar cada test según el comportamiento que comprueba. Distinguir un año calendario de un período móvil de 12 meses. | Renombrar el test de generación para expresar “rolling 12 months” y ejecutar `cd backend && pytest -q tests/test_routes.py`. |
| Documentación de validación sincronizada | Documentación y suites de pruebas | **T1/D2:** [verification.md](../../verification.md) registra 12 tests; [test_routes.py](../../backend/tests/test_routes.py) contiene 15 funciones `test_`. | Actualizar conteos y estado de validación cuando cambie la suite; calcularlos desde la salida del runner, no copiarlos de una cifra anterior. | Ejecutar `cd backend && pytest --collect-only -q` y corregir el conteo en `verification.md` para que coincida. |
| Contrato temporal probado | Generador backend y visualización frontend | **A3/T2/T3:** el período de UI no se deriva de la API y [test_routes.py](../../backend/tests/test_routes.py) no comprueba el rango generado. | Añadir pruebas que cubran el rango temporal real y evitar aserciones atadas a un año fijo cuando la generación depende de la fecha actual. | Añadir un test que valide que la respuesta generada cubre los 12 meses completos anteriores a `date.today()`; ejecutar `cd backend && pytest -q tests/test_routes.py`. |
| Estados de carga y error comprobables | Frontend y llamadas HTTP | **T2/X2:** [App.tsx](../../frontend/src/App.tsx) carga datos una vez; [financial-utils.test.ts](../../frontend/src/lib/financial-utils.test.ts) solo prueba utilidades. | Cubrir éxito y fallo de la petición con el runner Vitest. Mantener el comportamiento de error de la interfaz verificable sin depender de un backend externo. | Extraer la función de petición a un módulo de `src/lib`, añadir un test Vitest para una respuesta HTTP fallida y ejecutar `cd frontend && npm test`. |
| Instrucciones distintas para Docker y host | Documentación y configuración Vite | **X1:** [vite.config.ts](../../frontend/vite.config.ts) usa `backend:8000`, nombre DNS del servicio Compose; [README.md](../../README.md) documenta `VITE_API_BASE_URL`. | Explicar que el proxy predeterminado está orientado a Compose y documentar el origen que debe usarse al ejecutar Vite fuera de Docker. | Añadir a README un ejemplo de `VITE_API_BASE_URL` para backend en `localhost:8000`; comprobar la carga desde `npm run dev` con el backend local. |
| Backend listo antes de cargar el dashboard | Compose y arranque de la aplicación | **X2:** [docker-compose.yml](../../docker-compose.yml) usa `depends_on` sin healthcheck y [App.tsx](../../frontend/src/App.tsx) no reintenta la petición inicial. | No depender solo del orden de inicio de contenedores. Configurar una señal de salud del backend o una política de reintento y verificar el inicio conjunto. | Añadir un healthcheck del endpoint `/health` y una condición de dependencia saludable en Compose; validar con `docker compose config` y levantar ambos servicios. |
| Errores útiles para diagnóstico | Manejo de fallos frontend | **X4:** [App.tsx](../../frontend/src/App.tsx) reemplaza el fallo por un mensaje genérico y no registra el error original. | Conservar el mensaje visible para el usuario, pero registrar contexto suficiente para distinguir errores de red y respuestas HTTP fallidas. No ignorar silenciosamente la causa. | Añadir registro del error capturado en `App.tsx`; detener el backend, provocar el fallo y comprobar mensaje de UI y detalle en la consola. |
| Dependencias Python reproducibles | Backend y construcción de imágenes | **X3:** [requirements.txt](../../backend/requirements.txt) lista dependencias sin versiones. | Fijar versiones compatibles para las dependencias directas y actualizar esos límites de forma intencional, validando la instalación y las pruebas. | Fijar la versión de FastAPI que resuelva el entorno de desarrollo y ejecutar la instalación desde `backend/requirements.txt` seguida de `cd backend && pytest -q`. |
| Instrucciones de agentes mantenidas | Reglas y documentación de contribución del repositorio | **D1:** [AGENTS.md](../../AGENTS.md) dirige a `.agents/rules`, `.agents/skills` y `memory-bank`; no se encontraron archivos en esas ubicaciones al analizar el proyecto. | Mantener las rutas de instrucciones alineadas con los archivos existentes. No instruir a los agentes para que sigan reglas o memoria inexistentes. | Añadir a `AGENTS.md` un enlace directo a este archivo y verificar que la ruta relativa resuelve desde la raíz del repositorio. |
